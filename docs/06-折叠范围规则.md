# 折叠范围规则（start 只记位置、done 折到上一个边界、需求完成折全部）

这份文档定死一次折叠到底收走哪一段，是 `lib/region.js` 的 `foldRange()` 与
`verify-region.mjs` 的共同依据。

## 1. 一句话规则

折叠由 **`tree_task_done`** 触发，一次调用只折一次，折的是**触发点之前、上一个锚点之后**那一段过程：

| 触发 | 锚点（起点） | 收走 |
|---|---|---|
| `tree_task_done`（任务 / 步骤） | **上一个 `done` 或 `start`**（尚未 start 时退到 `create`） | 它的返回之后 → 这次 `done` 之前 |
| `tree_task_done`（**需求**） | 这条需求**开工**的那次 `tree_task_create`（上一次完成需求之后最早的那次） | 开工之后 → 这次 `done` 之前（**全部**） |

`tree_task_start` **不触发折叠**，只记录开工位置：start 之前遗留的过程一直留着，
等这条需求完成时由那次 `done` 一并收走；start 之后的过程由每次 `done` 收走。

边界只有三个工具名：`tree_task_create`、`tree_task_start`、`tree_task_done`，**按工具名认，不看实参**。
**`tree_task_plan` 不是边界**——它的调用与返回跟普通过程一样，落在区间里就被收走。

`create` 自己**不触发**折叠：它只是起点标记，记下这件事的时候还没有过程可收。

**能收多少，取决于模型什么时候报完成。** 区间再大也只在 `done` 那一刻收；几件任务全做完再连着补
`done`，中间那段就全程留在上下文里。所以「做完一个就立刻完成」是这条规则的前提，不是风格建议——
实测过一次对照：攒着补报的那一轮，用插件的会话每步平均输入 174.7k，不用插件的对照组 167.0k。

## 1.1 为什么边界必须各有专门的名字

写树的两个动作——「新建需求」与「给节点加子节点」——看起来可以并成一个
`tree_task_plan`（不填 `parentId` 就是建）。**不能。** 边界是"上一次调用之后"这种位置判定，
`plan` 在任务中途反复调用（每补一次步骤就调一次）。并成一个工具之后：

- 起点会被任务中途的 `plan` 不断往后推，`done` 与它之间那段过程再也进不了任何区间；
- 想靠"实参里有没有非空 `parentId`"来区分，等于把"认对边界"的责任交给模型的一次参数书写。
  写漏一个字段，起点就悄悄挪走，**而且不报错**。

所以要按**工具名**认，不依赖任何实参内容。

## 1.2 为什么 `start` 不折、`done` 认边界

- **`start` 只是位置标记。** 开工那一刻还没有值得收的过程；把 start 当折叠点，会把
  "记录开工"变成一次上下文重写，也会让"上一次折到哪儿"需要额外的游标来维持。
- **`done` 收的就是它前面这一小节。** 上一个 `done`（或 `start`）已经把范围划清了，
  起点直接取边界，不需要游标。
- **start 之前那段不丢。** 需求完成时，起点退到这条需求开工那次 `create`，start 之前
  遗留的过程连同中间的任务级通告一起收走，整条需求只留一条通告。
- **被挡下的过程也不丢。** 折叠会被「用户的话还没写进需求」挡住（§3.5）；挡下的那段
  留在表层，等这条需求完成时一并收走。

## 2. 记法

| 记号 | 含义 |
|---|---|
| `C` | 一次 `tree_task_create` 调用**连同它的 `tool/result`**；**边界** |
| `S` | 一次 `tree_task_start` 调用连同它的返回；**边界** |
| `D` | 一次 `tree_task_done` 调用连同它的返回；**边界** |
| `P` | 一次 `tree_task_plan` 调用连同它的返回；**不是边界**，可被折叠 |
| `w` | 过程：读文件、跑命令、assistant 消息、`tool/result` 等 |
| `H` | 真人消息（`source.kind === "user"`） |
| `N` | 上一次折叠落下的通告 |

## 3. 三条判定

### 3.1 终点

从末尾往前找**最近的一次 `D`**。找不到（比如刚 `C` 完，或刚 `S` 完）→ 本轮不折。
`S` 不是触发点：它只记录开工位置；`C` 也不是。

### 3.2 起点

**`D`（done）**：

1. 这次 `D` 指向的 id 是一条**需求** → 走 §3.6，起点退到它开工那次 `C`；
2. 否则 → 这次 `D` 之前**最近的一次边界调用**（`C` / `S` / `D`）；没有 → 表层第一个节点之后。

### 3.3 区间

`from` = 起点那次调用的 `tool/result` **之后**；`to` = 终点那次调用**之前**。
起点调用本身、以及终点的调用与返回，都留在表层上。

向后走时跳过紧邻的两样东西：起点调用自己的 `tool/result`，以及**上一次折叠落下的通告 `N`**
（它已经是收过的结果，再收一次会一轮轮空折下去）。
**例外**：需求级折叠（§3.6）反过来要收 `N`——那些通告正是这条需求的历史。

### 3.4 两条硬约束

- 区间里**夹着真人消息**（`H`）时，要看它**之后有没有一次「写需求」**：
  有 → 照折，那条用户消息连同过程一起收走；没有 → 整段不折，一个节点都不动
  （细则见 §3.5，判据在 `region.foldBlockReason`）；
- 区间**为空**（`from > to`）→ 什么都不注入，不追加、不留空消息。

### 3.5 用户输入可被折叠的前提

**「写需求」= `tree_task_create` 调用，或 `tree_task_requirement` 且 `action` 是
`confirm` / `update` / `confirmChange`。**

判据只有一条：**区间里最晚的那条用户消息之后，必须有过一次写需求**。
一次写需求盖住它之前的所有用户消息，所以只比最晚那一条就够。

- 满足 → 那条用户消息连同过程一起收走（它的内容已经进了需求的某个版本，
  **版本历史就是「用户说过什么」的账本**，折叠不丢纠偏）；
- 不满足 → 整段不折，并且由工具在返回里直说"哪一条用户消息还没写进需求"；
- `archive` / `prerequisites` / `question` 不算写需求：前两个改的是关联，`question`
  是"我还没看懂"，那一段更不该收。

边界要诚实说清：这条规则挡的是**"忘了写"**，挡不住**"糊弄写"**——写进去的东西有没有
真吸收，只有模型自己知道。

被挡下的那一段不会丢：它留在表层，等这条需求完成时由需求级折叠一并收走，见 §3.6 与场景 23。

### 3.6 需求完成时收走整条

`tree_task_done` 指向的 id 是一条**需求**时，起点不是"上一个边界"，而是
「**上一次完成需求**之后最早的那次 `C`」——也就是这条需求开工那一刻。
于是中间那些任务级通告 `N` **一并被收走**，不层层堆叠。

三处配套：

- 这一档**不跳过**紧邻的旧通告（普通折叠要跳过，否则会一轮轮空折）；
- 通告只报条数，不点名需求、不带笔记；
- 返回固定句式 `<id> 需求已完成，结果：<总结>`，后接后续需求或交付提示。

### 3.7 `start` 的返回

`tree_task_start` 返回固定句式 `<id> 需求开始，需求详情：` 加这条需求的 YAML 详情
（`renderDetail`：简介、详情、前置、任务与步骤）。
start **不折叠**：它只记录开工位置，start 之前的过程留到需求完成时收走。

## 4. 与上一版的差异

| 版本 | 起点取谁 | 触发 |
|---|---|---|
| 更早 | 表层里**上一个边界调用**（`create` / `plan` / `done` 都算边界） | `done` |
| 上一版 | 上一次 `done` 之后的第一条 `create` | `done` |
| 上一版（start 折叠） | `start` 取**上次折叠成功处**；`done` 取**上一个边界**；需求完成取名下那条 `create` | `start` / `done` |
| **本版** | `start` **不折**；`done` 取**上一个边界**；需求完成取名下那条 `create` | **`done`** |

两点效果：

- **开工不再重写上下文**：`start` 只记位置，它的调用与返回都留在表层。
- **start 之前那段仍有归宿**：需求完成时整条收起；被挡过的过程不必靠下一次 `start`
  补折，等需求完成时一起收走。

按阶段推进读这张表：真实会话里每次 `agent/pre-step` 只折一次，触发那一刻表层上只到那一次
`D` 为止。`N0` 表示"这一次折叠之前没有成功折过"。

| # | 表层序列（早 → 晚） | 触发 | 起点 | 收走 | 留下 |
|---|---|---|---|---|---|
| 1 | `C w S` | 不折（没有 `D`） | — | 无 | 全部 |
| 2 | `C w S w D` | `D` | `S` | `w` | `C S D` |
| 3 | `C w S`（折过）`w D` | `D` | `S` | `w` | `N C S D` |
| 4 | `C w S`（折过）`w S2` | 不折（`S` 不触发） | — | 无 | 全部 |
| 5 | `C w S w`（被挡，没折）`w S2` | 不折（`S` 不触发）→ 等需求完成 | — | 无 | 全部 |
| 6 | `C D`（紧邻） | `D` | `C` | 空 → 不注入 | 全部 |
| 7 | `C P D` | `D` | `C` | `P` 的调用与返回 | `C D` |
| 8 | `C w D1 w P w D2` | `D2` | `D1` | `w P w` | `C D1 D2` |

## 6. 实现要点

`foldRange(session, plan, cursors)` 的结构（`lib/region.js`）：

```
1. 从末尾往前找最近一次 D → endIdx；找不到 → return null
2. D 指向一条需求 → requirementId；否则 null
3. 默认 startIdx = endIdx 之前最近的一次边界调用（C / S / D）
4. requirementId 非空 → 锚点 = 上一次完成需求；起点 = 锚点之后最早的 C，没有就退回锚点
5. from = startIdx === -1 ? 1 : startIdx + 1
   while (from < endIdx)：跳过 tool/result；**普通折叠**还要跳过紧邻的插件通告
   to = endIdx - 1；from > to → return null
6. 返回 { from, to, endIdx, requirementId, trigger, shadowed }
```

`foldOnce(ctx, session, plan, store, cursors)` 在成功之后把 `cursors.foldedAt` 记成
**刚插进去的那条通告的 seq**（`surface.nodes[range.from]`）。这个游标只给界面与排查用，
不参与折叠区间计算。

`previewFold(session, plan, cursors)` 是同一套判据的只读入口，工具用它把"这次收不走"
直接说在返回里。

## 7. 自检覆盖

`verify-region.mjs` 里与这条规则直接相关的场景：

| 场景 | 钉住的东西 | 判定表 |
|---|---|---|

| 2 | 末尾最近一次边界不是 `S` / `D` 时不折 | — |
| 3 / 3b | `C P D` 只收 `P`；`C D` 紧邻不注入 | 7 / 6 |
| 4 / 5 | 区间夹真人消息且其后没写需求 → 整段不折 | 10 |

| 11–14 | 分阶段推进、两次 `done` 紧邻、多次补 `P` | 8 / 9 |
| 17 | 需求完成：起点退到开工那次 `C`，中间的任务级通告一并收走 | 11 |
| 18 | 需求级折叠收走旧通告；通告里没有笔记 | — |

假 session 自带 `sourceEventSeqs` 全覆盖校验（少一个就抛），所以"被跨过的调用确实进了
替换清单"由每次 `foldOnce` 隐式钉住。

三级游标同步不受影响——游标不参与折叠区间计算（见 `docs/02` §4.1）。
`foldedAt` 是第四个游标位，只记位置，不参与折叠区间计算。
