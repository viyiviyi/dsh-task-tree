## 1. 系统提示词段落

`lib/prompt.js`。**只有一个段落**，注册名 `dsh-tree-task-flow`，默认 order `1800`。
段落正文**不随计划变化，也不复述工具清单**——计划状态由 `tree_task_status` 现取，
每个工具的用法由它自己的 `description` 承担。

注册形状（`text` 是函数：工具不在当前作用域时输出空串）：

```js
ctx.systemPrompt.section({
  name: "dsh-tree-task-flow",
  order: 1800,
  text: ({ scope }) => (ctx.tools.get("tree_task_status", scope) === undefined ? "" : SECTION_TEXT),
});
```

段落正文（`SECTION_TEXT`，一字不改）：

```
`tree_task_*` 工具适用长线任务，当目标和资料分析完成后，如果用户要求或判断任务较为复杂，可以将任务执行计划分为目标、任务、任务执行步骤三级写入任务树，借助工具来推进项目；将目标按照可独立交付的节点分为多个任务，任务节点需要准确表述清楚需求；将任务按照“需一次性处理并交付产物”分为多个步骤；完成步骤或任务时提交后续步骤需要的 result，提交内容可以是：产物/结论/问题/有哪些需要注意的坑；执行过程上下文将会在完成时被隐藏。
```

## 2. 七个工具的描述与参数 schema

`lib/tools.js`。全部以 `tree_task_` 开头，共七个；`parameters` 是**裸 JSON Schema**
（以 `link:` 方式安装的插件从自己目录往上找不到宿主的 schemastery）。

**写树分成两个工具，不是可以合并的重复。** `tree_task_create` 只管新建目标，
`tree_task_plan` 只管给已有的节点追加子节点——两者都是"一串 `{title, detail}`"，
分成两个名字才能按工具名认出"开工"那一下。理由与代价见 `lib/region.js` 顶部那段注释
与 `docs/06-折叠范围规则.md` §1.1：`create` 与 `done` 是折叠区间的两个边界，
`plan` **不是边界**、可被折叠；并成一个工具（不填 `parentId` 就是建目标）以后，
折叠起点就只能靠实参去猜，模型一次写漏或多写就会把起点挪走，那段过程再也收不走。

七个工具共用的返回形状（`OUTPUT`）：

```js
{
  schema: {
    type: "object",
    additionalProperties: false,
    properties: { text: { type: "string" } },
  },
  render: (_args, value) => [{ type: "text", text: String(value?.text ?? "") }],
}
```

### 2.1 `tree_task_status`

```yaml
description: "查看计划树：目标、任务、子任务各自的状态与已提交的结果，以及现在该推进哪个节点。任务开头、上下文被压缩之后、或者不确定下一步做什么时，调用它。默认只展开还没结束的目标——已经做完的目标只留目标那一行，要看它的完整树就把 id 填上。"
parameters:
  type: object
  additionalProperties: false
  properties:
    id:
      type: string
      description: "可选。填目标 id 就返回那个目标的完整树（已完成的目标默认不展开）；填任务或子任务 id，就按它所在的那个目标展开。"
```

`description` 在源码里是三段字符串用 `+` 拼起来的（上面是拼接后的结果，下同）；`parameters` 里**没有 `required`**。

### 2.2 `tree_task_create`

```yaml
description: "新建一个目标：这个目标 + 它下面的若干任务。**它是「开工」那一下**——折叠上下文时，插件就认这次调用作为「这一轮从哪儿开始」。一个会话可以有多个目标，按调用顺序排在计划里——已经建过的目标和它们的历史都留着，不会被这次调用替换掉。这里的任务是交付节点——一件能独立验收的交付内容，可以是需要完成或验证的某件事，也可以是一个检查点，不是步骤本身。建完记得用 tree_task_plan 给这个目标下的第一个任务拆子任务。"
parameters:
  type: object
  additionalProperties: false
  properties:
    title:  { type: string, description: "目标：一句话说清最终要达成什么" }
    detail: { type: string, description: "目标的补充说明" }
    tasks:
      type: array
      description: "目标下的任务列表（交付节点），按建议的执行顺序排列"
      items:
        type: object
        additionalProperties: false
        properties:
          title:  { type: string, description: "任务标题" }
          detail: { type: string, description: "任务的补充说明" }
        required: [title]
  required: [title, tasks]
```

`description` 在源码里是六段字符串用 `+` 拼起来的；`required` 是 **`title` 与 `tasks` 两个**。

### 2.3 `tree_task_plan`

```yaml
description: "给一个节点追加子节点：给**需求**追加任务，给**任务**追加步骤。任务是交付节点（一件能独立验收的事），步骤是「需要一次性做完」的那一下。步骤是最低一级，不能再往下拆。**读资料不算任务**：看用户的话、看需求详情、读相关文件与文档都是开工前该掌握的信息，先把该看的看完再拆；把它们列成节点只是白占一个格子，还会把折叠卡住。**建新需求不归它管，那是 tree_task_create**——它只往已有的节点上接子节点。"
parameters:
  type: object
  additionalProperties: false
  properties:
    parentId:
      type: string
      description: "父节点 id（目标或任务），例如 t-abc123"
    children:
      type: array
      description: "要追加的子节点，按执行顺序；父节点是目标时是任务（交付节点），是任务时是子任务（步骤）"
      items:
        type: object
        additionalProperties: false
        properties:
          title:  { type: string, description: "子节点标题" }
          detail: { type: string, description: "补充说明" }
        required: [title]
  required: [parentId, children]
```

`description` 在源码里是四段字符串用 `+` 拼起来的；`required` 是 **`parentId` 与 `children` 两个**，
顶层**不带** `title` / `detail` / `tasks`——建新目标不归它管。

### 2.4 `tree_task_done`

```yaml
description: "完成[步骤/任务/需求]并折叠过程：把节点标成完成、记下它的 result，插件随即把这段执行过程从上下文里折叠掉，只留一条携带该结果的汇总消息。id 给三级里哪一级都行。**必须写 result**：步骤的 result 一句话说清这步做了什么；任务的 result 写交付物与验收方式（文件在哪、怎么跑、验出什么、已知限制）；**需求的 result 就是它的总结**——做了什么、结论、坑、给后续需求的注意，别的需求靠它快速查阅。完成需求不需要用户点头，你判断做完了就完成它；最终成品的第一责任人是用户。"
parameters:
  type: object
  additionalProperties: false
  properties:
    id:     { type: string, description: "要完成的节点 id" }
    result:
      type: string
      description: "这个节点产出了什么。它整段执行过程会被这条结果顶替，所以要能独立看懂：任务写交付物与验收方式，子任务写清这步做了什么。"
  required: [id, result]
```

### 2.5 `tree_task_update`

```yaml
description: 修改一个节点的标题或说明。
parameters:
  type: object
  additionalProperties: false
  properties:
    id:     { type: string, description: "节点 id" }
    title:  { type: string, description: "新的标题" }
    detail: { type: string, description: "新的说明" }
  required: [id]
```

### 2.6 `tree_task_drop`

```yaml
description: "放弃一个节点：**这件事不做了**，划掉但留着可查。放弃需求会连同它下面没做完的任务与步骤一起放弃；完成过的保持原样（不改写历史）。**支持批量**：给 ids 一次放弃一批，父节点带走的子孙自动跳过，不重复处理。如果这条内容本身就写错了，用 tree_task_delete 删掉，不要用这个。"
parameters:
  type: object
  additionalProperties: false
  properties:
    id:  { type: string, description: "要放弃的节点 id" }
    ids: { type: array, items: { type: string }, description: "要放弃的一批节点 id" }
```

### 2.7 `tree_task_delete`

```yaml
description: "删掉一个节点——**清理**用的，不是「这件事不做了」。放弃（tree_task_drop）是留个记号：这件事我不做，但还查得到它曾经有过；删除是把内容凭空摘掉，连同它下面的东西一起，**不看状态**（已完成、已放弃的都删得掉）。**支持批量**：给 ids 一次删一批，父节点带走的子孙自动跳过，不重复处理。内容写错了、建重了、结果记在了错的地方，就用这个。"
parameters:
  type: object
  additionalProperties: false
  properties:
    id:  { type: string, description: "要删除的节点 id" }
    ids: { type: array, items: { type: string }, description: "要删除的一批节点 id" }
```

**参数里为什么没有"确认"开关。** 删除是给模型用的常规手段——它自己把树写错了就自己清掉，
多一层确认只会让这件事做不成。真正要拦住的是**人**在面板上误点，那道闸门在界面那一侧
（`client.js` 的 `confirm.delete`）。

## 3. 每种情况下的工具返回原文

七个工具一律返回 `{ text }`，由 `OUTPUT.render` 渲染成一个文本块。下面每一格都是**返回正文**
（换行按源码原样）。

### 3.1 树渲染（多数返回都会带一份）

`lib/plan.js` 的 `renderTree(plan, only = null)` 与 `renderGoal(goal, plan, expand = true)`
输出的是**规范的 Markdown 嵌套任务清单**，每层缩进两个空格（`INDENT = "  "`）。形状：

```markdown
- [ ] **目标** `g-xxx` <目标标题>
  - **说明**：<目标的 detail，若有>
  - **结果**：<目标结果全文>
  - [ ] **任务** `t-xxx` <任务标题> ← 当前
    - **结果**：<任务结果全文>
    - 还没有子节点，用 tree_task_plan 补上
    - [ ] **子任务** `s-xxx` <子任务标题> ← 当前
      - **结果**：<子任务结果全文>
```

| 元素 | 规则 |
|---|---|
| 节点行 | `- ` + 标记 + `**层级**` + 反引号 id + 标题；第三级写「子任务」 |
| 标记 | `[x]` 已完成（done）、`[-]` 已丢弃（dropped）、其余 `[ ]`（pending） |
| `← 当前` | 活动路径上的节点；任务行在"它就是当前任务"或"它是检查点节点"时带上 |
| `- 还没有子节点，用 tree_task_plan 补上` | 只在该任务未结束且一个子任务都没有时出现 |
| `- **说明**：` 行 | 只有**目标**有（`renderGoal` 只对 `goal.detail` 调 `pushField`）；空值不输出 |
| `- **结果**：` 行 | 只在提交过 `result` 时出现；**全文输出，一个字都不截**；多行正文逐行输出，续行比该行再多缩进两个空格，空行也带上缩进 |
| 多个目标 | 每个目标渲染成一段，段与段之间直接换行（`join("\n")`），不插空行 |
| 没有计划时 | 渲染成 `（还没有计划。用 tree_task_plan 建立目标与任务。）` |
| 指名 id 但找不到 | `找不到节点 <id>。不带 id 调用可以看到本会话的全部目标。` |

### 3.2 `tree_task_status`

| 情况 | 返回 |
|---|---|
| 不填 `id` | `renderTree(plan, null)`：全部目标，但**已经结束（done / dropped）的目标只渲染目标那一级**（`expand = isOpen(goal)`） |
| 填了 `id` | 该 id 所在目标的**完整树**（填任务或子任务 id，就展开它所在的那个目标） |
| 填了 `id` 但找不到 | `找不到节点 <id>。不带 id 调用可以看到本会话的全部目标。` |
| 没有计划 | `（还没有计划。用 tree_task_plan 建立目标与任务。）`（填不填 `id` 都一样） |

### 3.3 `tree_task_create`

判定顺序就是 `execute` 里的顺序——先看本会话有没有计划，再决定是建计划还是追加目标：

| 情况 | 返回 |
|---|---|
| 本会话还没有计划 | `计划已建立，目标「<目标标题>」。` + 空行 + **那个目标的树** + 空行 + `下一步：给这个目标下的第一个任务拆子任务——用 tree_task_plan，parentId 填那个任务的 id。` |
| 已有计划 | `已新增目标「<目标标题>」。` + 空行 + **那个目标的树** + 空行 + 同一句"下一步" |
| `createPlan` / `addGoal` 抛错（兜底分支） | `建立目标失败：<错误消息>`。schema 已把 `tasks` 列为必填，所以 `createGoal` 那句"至少要有一个任务；请在 tasks 里给出"只在实参绕过校验时才走到，这层 try/catch 是防将来改动的兜底 |
| `title` 为空 | 不报错：`normalizeTitle` 给占位标题 `(未命名目标)`，照常建起来（原有兜底行为） |

### 3.4 `tree_task_plan`

**只能给已有的节点追加子节点**，判定顺序就是 `execute` 里的顺序：

| 情况 | 返回 |
|---|---|
| 本会话还没有计划 | `还没有计划。先用 tree_task_create 建立目标与任务。` |
| 找不到父节点 | `没有添加：找不到节点 <parentId>` |
| 父节点是子任务 | `没有添加：子任务 <parentId> 是最低一级，不能再拆` |
| `children` 不是数组或为空 | `没有添加：children 至少要给一个子节点。` |
| 成功（父节点是目标） | `已添加 <N> 个任务：` + 每行 ``- `<id>` <标题>`` + 空行 + **该父节点所在那个目标的树** |
| 成功（父节点是任务） | `已添加 <N> 个子任务：` + 每行 ``- `<id>` <标题>`` + 空行 + **该父节点所在那个目标的树** |

`addChildren` 内部先找父节点、再判层级、最后判 `children`，所以"找不到父节点"与
"不能拆子任务"排在"至少要给一个子节点"之前。

**写树类工具（`tree_task_create` / `tree_task_plan` / `tree_task_update` / `tree_task_drop`）
都只返回"本次动到的那个目标"的树**（`renderGoal(<那个目标>, plan, true)`），不再倾倒整棵树；
要总览用 `tree_task_status`。

### 3.5 `tree_task_done`

| 情况 | 返回 |
|---|---|
| 没有计划 | `还没有计划。` |
| 找不到节点 | `没有完成：找不到节点 <id>` |
| 该节点已完成 | `没有完成：节点 <id> 已经是完成状态` |
| 该节点已丢弃 | `没有完成：节点 <id> 已被丢弃，不能标记完成` |
| `result` 为空（或全空白） | `没有完成：完成<层级>必须提交结果：请在 result 里写清它产出了什么`（层级 = `目标` / `任务` / `子任务`） |
| 成功 | `tree_task消息：` + 下面五种"下一步"之一 |

成功的五种落点（按优先级判断，`lib/plan.js` 的 `continueNote`）：

| # | 情形 | 返回正文 |
|---|---|---|
| 1 | 父节点进入检查点（子节点全结束、自己还没完成） | `tree_task消息：检查点：<自称> 的<任务｜步骤>已全部结束，请确认<自称> 是否完成，如果完成请调用tree_task_done，如果还需继续，可使用 tree_task_plan 新增<任务｜步骤>继续。` |
| 2 | 整棵树都结束了 | `tree_task消息：请汇报最终结果。` |
| 3 | 同层还有下一个子任务 | `tree_task消息：接下来需要进行步骤：「<标题>」(<id>)。` |
| 4 | 当前任务没有待办的子任务（一个都还没拆，或拆下的都已结束），而整棵树还没收尾 | `tree_task消息：接下来需要进行任务：「<标题>」(<id>)。` |
| 5 | 当前目标下还没有任务 | `tree_task消息：接下来需要进行目标：「<标题>」(<id>)。` |

判断顺序就是表的顺序（`continueNote`）：检查点 → 整棵树结束 → 步骤 → 任务 → 目标，
前一条不成立才看下一条。源码里这套提示同时以 `{ lead, text }` 返回：检查点的 `lead` 是 `。`，
其余是 `，`，供"完成通告 + 下一步提示"拼成一句话；`tree_task_done` 的返回只用 `text`。

`<自称>` 的写法（`subject()`）：目标是 `目标<id>`（**不带标题**），任务是
`任务「<标题>」<id>`，子任务是 `步骤「<标题>」<id>`。

> 注意层级词在不同场合不一样：**树渲染**里第三级叫「子任务」，**注入消息与
> `tree_task_done` 返回**里第三级一律叫「步骤」。

### 3.6 `tree_task_update`

| 情况 | 返回 |
|---|---|
| 没有计划 | `还没有计划。` |
| 找不到节点 | `没有修改：找不到节点 <id>` |
| 既没给 title 也没给 detail | `没有修改：没有给出任何要改的字段（title / detail）` |
| 成功 | `已更新 <title / detail>。` + 空行 + **该节点所在那个目标的树**（改了哪个就写哪个，多个用 ` / ` 连接） |

### 3.7 `tree_task_drop`

| 情况 | 返回 |
|---|---|
| 没有计划 | `还没有计划。` |
| 找不到节点 | `没有丢弃：找不到节点 <id>` |
| 该节点已完成 | `没有丢弃：节点 <id> 已经完成，丢弃会毁掉它的结果记录` |
| 该节点已丢弃 | `没有丢弃：节点 <id> 已经被丢弃` |
| 成功 | `已丢弃：<目标「a」、任务「b」、子任务「c」>` + 空行 + **该节点所在那个目标的树** + 空行 + `<下一步提示>` |

成功时被连带丢弃的节点会按「目标 → 任务 → 子任务」的顺序列在同一行、用 `、` 分隔；
末尾的下一步提示就是 `continueNote` 的 `text`（**不带** `tree_task消息：` 前缀，
也不带前导标点）。已经结束的子节点保持原样——丢的是"还要不要做"，不改写历史。

### 3.8 `tree_task_delete`

| 情况 | 返回 |
|---|---|
| 没有计划 | `还没有计划。` |
| 找不到节点 | `没有删除：找不到节点 <id>` |
| 成功（删的是任务或子任务） | `已删除：<目标「a」、任务「b」、子任务「c」>` + 空行 + **该节点所在那个目标的树** + 空行 + `<下一步提示>` |
| 成功（删的是目标） | `已删除：<目标「a」、任务「b」…>` + 空行 + `这个会话还剩 <n> 个目标，要看细节用 tree_task_status。` + 空行 + `<下一步提示>` |
| 成功（删的是最后一个目标） | `已删除：…` + 空行 + `计划树现在空了。（要用就用 tree_task_create 建新目标。）` + 空行 + `<下一步提示>` |

**没有"已完成就不能删"这一行。** 这是它与丢弃最大的区别：丢弃拒已完成（结果记录不该被改写），
删除**不看状态**——内容本身就是错的，摘掉正是目的。被摘掉的节点连同它的子孙、连同它们提交过的
`result` 一起从计划里消失。

**删目标时为什么不渲染树。** 写树类工具的规矩是"只返回本次动到的那个目标"，可那个目标已经
不存在了，没有"它所在的树"可给，所以退回报一句剩余目标数。要看细节再调 `tree_task_status`。

**删空之后 `goals` 是空数组，不是没有计划。** 计划文件照旧在盘上（`renderTree` 会说"还没有计划"），
`activePath()` 是 `null`，面板按"没有目标"处理。

被摘掉的节点按「目标 → 任务 → 子任务」的顺序列在同一行、用 `、` 分隔；末尾的下一步提示与丢弃
同源（`continueNote` 的 `text`，不带 `tree_task消息：` 前缀、不带前导标点）。

## 4. 折叠范围的各种情况

折叠由 `agent/pre-step` 监听器完成（工具本身不注入消息、不动 surface）。规则**只看表层，
与计划树无关**。完整推导见 `docs/06-折叠范围规则.md`，这里给出可直接使用的判定表。

### 4.1 记法

写树分成两个工具，所以**按工具名**就能分清身份：`tree_task_create` 是 `C`，
`tree_task_plan` 是 `P`（记法与判定表同 `docs/06-折叠范围规则.md`）。

| 记号 | 含义 |
|---|---|
| `C` | 一次 `tree_task_create` 调用**连同它的 `tool/result`**（下同）；**边界，且是起点首选** |
| `P` | 一次 `tree_task_plan` 调用连同它的返回；**不是边界**，与普通过程一样可被折叠 |
| `D` | 一次 `tree_task_done` 调用连同它的返回；**边界** |
| `w` | 过程：读文件、跑命令、assistant 消息、`tool/result` 等 |
| `H` | 真人消息（`source.kind === "user"`） |

### 4.2 五条判定（按顺序）

1. **终点**：表层里**最近的一次边界调用必须是 `D`**。不是 `D`
   （说明还没走到"完成"这一步）或表层里根本没有边界调用，本轮不折。
2. **基准 floor**：上一次 `D` 的位置之后（`prevDone + 1`）。**更早没有 `D` 时，floor 是
   表层开头**（节点 0 是系统提示词，受 DSH 重写保护，永远不进替换区间）。
3. **起点**：从 floor 到本次 `D` 之间，取**最早**的那次 `C`。区间里一次 `C`
   都没有时，起点回退到 floor 自己（即上一次 `D` 的调用位置；更早没有 `D` 时回退到
   "表层第一个节点之后"）。
4. **区间**：起点那次调用的 `tool/result` **之后** → 本次 `D` 的调用**之前**。
   起点那次调用本身、以及本次 `D` 的调用与返回，都留在表层上。
   向后走时继续跳过紧邻的两样东西：起点调用自己的 `tool/result`，以及**上一次折叠落下的通告**
   （它已经是收过的结果，再收一次就会一轮轮空折下去）。
5. **两条硬约束**：区间里**夹着真人消息** → 整段不折，一个节点都不动；区间**为空**
   （`from > to`）→ 什么都不注入，不追加、不留空消息。

要点：边界调用是 `tree_task_create` 与 `tree_task_done` 两个名字，
**`tree_task_plan` 不是边界**——它跟普通过程一样，落在区间里就被收走。
起点首选只认 `C`（新建目标），而 `C` 按工具名认、不看实参：这正是 `create` 与 `plan`
不能并成一个工具的原因——并起来就只能靠"实参里有没有 `parentId`"去猜，
模型一次写漏或多写就会把起点挪走，那段过程再也收不走（推导见 `docs/06-折叠范围规则.md` §1.1）。
像 `D1 → w → P → w → D2`（其间没有 `C`）这种序列，起点回退到 `D1` 之后，
`w P w` 全部收走。

### 4.3 判定表

**按阶段推进读这张表**：真实会话里每次 `agent/pre-step` 只折一次，触发那一刻表层上
只到那一次 `done` 为止。所以同一个序列会分几次折，表中用"触发"列区分。

| # | 表层序列（早 → 晚） | 触发 | 起点 | 收走的区间 | 留在表层 |
|---|---|---|---|---|---|
| 1 | `C w P w D` | `D` | `C` | `w P w` | `C D` |
| 2 | `C w D` | `D` | `C` | `w` | `C D` |
| 3 | `C D`（紧邻，中间没有别的调用） | `D` | `C` | 空 → 不注入 | 全部 |
| 4 | `C P D`（只隔一次 `plan`） | `D` | `C` | `P` 的调用与返回 | `C D` |
| 5 | `C P D1 D2` | `D1` | `C` | `P` 的调用与返回 | `C D1` |
| 　 | 　 | `D2` | 回退 `D1` | 空 → 不注入 | `C D1 D2` |
| 6 | `C w D1 w D2` | `D1` | `C` | `w` | `C D1` |
| 　 | 　 | `D2` | 回退 `D1` | `w` | `C D1 D2` |
| 7 | `C w D1 w P w D2` | `D1` | `C` | `w` | `C D1` |
| 　 | 　 | `D2` | 回退 `D1` | `w P w` | `C D1 D2` |
| 8 | `D1 w C w D2` | `D2` | `C` | `w` | `D1 C D2` |
| 9 | `D1 w P w D2`（其间没有 `C`） | `D2` | 回退 `D1` | `w P w` | `D1 D2` |
| 10 | `C w H w D` | `D` | `C` | `w H w` 含真人消息 → 整段不折 | 全部 |
| 11 | 表层里找不到 `C`（被压缩遮掉） | `D` | 表层第一个节点之后 | 多半撞上真人消息 → 不折 | 全部 |

第 7 行与第 9 行是这条规则的关键：`P` **不是**边界、也不参与起点判定，所以 `D1` 与 `P`
之间那段过程不会漏网，`P` 自己也会被收走。完整推导、边界情形与旧版对照见
`docs/06-折叠范围规则.md`。

### 4.4 折叠通告的形态

折叠落地时追加的是一条 `user/message`（`source` 形如
`{ kind: "plugin:dsh-tree-task-flow", form: "notice", summary: <一行摘要> }`；
**不是**老写法 `{ kind: "plugin", plugin: "dsh-tree-task-flow" }`——那个在 v4 会话里
会被 DSH 的落盘校验拒掉，见 §4.6），正文（`renderSummary`）：

> **所有通知的摘要都带同一个前缀。** 本插件的通知有六种（折叠、压缩、恢复续行、
> 计划续行、中断拉起、中断重试），界面上都是一行摘要，**每一行都以
> `树形任务流 · ` 开头**——不写前缀，人看不出这条是谁发的。
> 前缀只在 `lib/region.js` 的 `pluginSource()` 里加一次，调用点只写裸标签
> （「恢复续行」「中断拉起」……）；要按摘要做匹配用 `hasSummary(source, label)`，
> 它带不带前缀都认（升级前落下的老消息没有前缀）。

```
tree_task消息：此处隐藏了<N>条过程上下文。
其中修改或生成了文件：
<路径>
```

- 文件那一行**只在有写入文件时**出现；路径取自工具调用的 `file_path` / `path` 参数，
  只认 `write` / `edit` / `str_replace_editor`（写入），去重、按出现顺序；读取类调用
  （`read` / `read_image`）不列，`pwsh` / `bash` 里碰过什么文件看不出来，也不计入。
- 界面上的折叠标题（`summary`）：`树形任务流 · 此处隐藏了<N>条过程上下文`，
  有写入时追加 ` · 修改或生成 <k> 个文件`。
- 通告**只讲折叠**：不带任务、需求、笔记的提示——那些由工具返回负责。
- **不重复提交内容**：`result` 就在这次 `tree_task_done` 的参数里，通告里不抄第二遍。
- 被折叠的节点是完成还是丢弃，通告只报条数，不区分。

### 4.5 与 `tree_task_done` 返回的关系

两者合起来才是一句完整的话：**通告落在触发这次折叠的 `tree_task_done` 调用之前**，
这次调用的参数与返回都留在通告之后：

```
[user/message]  tree_task消息：此处隐藏了4条过程上下文。
[tool/result]   t-4 任务已完成，结果：<result>
                后续：接下来需要进行步骤：「步骤二」(s-4)。
```

第一行是折叠**落下的通告**，后两行是这次 `tree_task_done` 的**返回**。注意通告报的是
"收走了多少条过程"，**不是**"哪个节点完成了"——节点的状态与结果始终在树里
（`tree_task_status` 或各工具返回附带的那份树）。那一段过程里若夹着 `tree_task_plan`
的调用与返回，它**不是边界**，跟着一起收走；`tree_task_create` 与两次 `tree_task_done`
的调用与返回都留在表层上。

### 4.6 压缩提醒的形态

DSH 内置压缩落下检查点之后，如果这个会话有计划树，追加的也是一条同样形态的
`user/message`（`source` 同样是 `{ kind: "plugin:dsh-tree-task-flow", form: "notice" }`），
正文：

```
tree_task消息：上下文刚被压缩过，计划树没有被压缩。用 tree_task_status 取回当前进度、各节点已提交的 result，以及下一步该推进哪个节点。
```

- 界面上的 `summary`：`树形任务流 · 上下文被压缩，计划树仍在`。
- 与折叠通告的区别：它用 `surfaceOp: "append"`（只追加、不替换），
  折叠通告用的是 `replace`。
- 认压缩的依据是表层上那条 `user/message` 的 `source`——**两种形状都认**：
  v4 原生的 `{ kind: "compact-checkpoint", compactionId, … }`，与还没迁移的
  v3 会话里的老写法 `{ kind: "plugin", plugin: "compact" }`。**不是**
  `compaction/summary` 事件——那个事件不带 `surfaceOp`，根本不在表层里。
- 同一个检查点只提醒一次，位置记在 `surfaces/<sessionId>.json` 的 `compactionNoticeAt`。
- 实现与已知限制见 `lib/compaction.js` 与 `docs/02-DSH插件开发方案.md` §4.8。

## 5. 状态文件

全部在 `$DSH_HOME/dsh-task-tree/` 下。除 `settings.json` 外都**以 `sessionId` 为键**（`lib/store.js`）：

| 文件 | 内容 |
|---|---|
| `plans/<sessionId>.json` | 计划树（每个会话一棵；`tree_task_create` 每次调用追加一个目标，不替换整棵树） |
| `surfaces/<sessionId>.json` | 三层进度游标 `{ key, cursor }` 与压缩提醒的已提示位置 `compactionNoticeAt`——**不参与折叠**，只给界面看 |
| `held/<sessionId>.json` | `{ sessionId, paused, stopped, at }`：「被按住」的持久状态，重启后仍然有效 |
| `settings.json` | 在插件配置页里改过的开关 `{ autoContinue?, interruptRecovery? }`——**整个插件一份，不按会话分**；键的名单只由 `lib/settings.js` 的 `SETTING_KEYS` 定义 |

- 写入一律走「临时文件 + rename」；读到的坏文件按空状态处理。
- 插件**绝不直接写会话日志**：会话里的一切都走 `session.append()`。
- `held` 的两半互补更新（`paused` 归暂停闸门、`stopped` 归自动续行），两份都不是 `true` 时删文件。
- `settings.json` 只记**在插件配置页里改过的**键；生效优先级是 **插件页 > profile 的 config > `DEFAULT_CONFIG`**，所以删掉这个文件就等于回到 profile 与默认值。

## 6. 面板接口（HTTP）

条目跑在浏览器里，拿不到宿主内存里的 store，数据只能走这三个端点（`lib/http.js`），
前缀都是 `/dsh-tree-task-flow/`：

| 端点 | 方法 | 作用 |
|---|---|---|
| `/tree?sessionId=…` | GET | 一棵树的全部信息：`plan` + `active` + `checkpoint` + `results` + 三层游标 + `paused` / `stopped`。这个会话没有计划时 404。 |
| `/settings` | GET | **与会话无关**的一份：`{ enabled, settings: { autoContinue, interruptRecovery } }`。插件管理里那一页走这里——它不是某个会话的界面，没有"当前会话"这个概念，所以它不能走 `/tree`。 |
| `/action` | POST | 条目与插件配置页上的每个按钮都走这里，体是 `{ sessionId, action, … }`。 |

`action` 一共六种：

| action | 入参 | 成功返回 |
|---|---|---|
| `pause` / `resume` | — | `{ paused, stopped, message, woke }`。`message` 是给界面看的一句话（放行了 / 正在跑不用唤醒 / 先打开它），`woke` 表示这次有没有真推过消息。 |
| `done` | `id`、`result` | `{ events, active, checkpoint, results }`。**`result` 必填**。 |
| `drop` | `id` | 同上，`events` 是被连带丢弃的节点。 |
| `delete` | `id` | 同上，`events` 是被摘掉的节点——**真删，任何状态都能删**。 |
| `setting` | `key`、`value` | `{ settings: { autoContinue, interruptRecovery } }`。 |
| `reset` | — | `{ active: null, checkpoint: null, results: null }`，同时清掉三层游标。 |

几条边界：

- 写树的三种（`done` / `drop` / `delete`）失败时返回 **200 + `{ ok: false, error }`**——失败原因是业务事实（"已经完成"、"找不到节点"），不是 HTTP 层的事。
- `setting` 的入参不合法返回 **400**：`key` 不在 `SETTING_KEYS` 里、或 `value` 不是布尔，都直接拒掉。这一项**不读 `sessionId`**（设置是整个插件一份），但接口形状仍然统一，带上这个字段也不会被用。
- **`resume` 是无条件的**：不管此刻有没有闸门挂在岔口上、会话忙不忙，它都当场解除"被按住"，然后才谈要不要主动唤醒（见 `lib/pause.js` 模块头的 ★）。
