## 1. 系统提示词段落

`lib/prompt.js`。**只有一个段落**，注册名 `dsh-tree-task-flow`，默认 order `1800`。
段落正文**不随计划变化，也不复述工具清单**——计划状态由 `tree_task_status` 现取，
每个工具的用法由它自己的 `description` 承担。

注册形状（`text` 是函数：工具不在当前作用域时输出空串）：

```js
ctx.systemPrompt.section({
  name: "dsh-tree-task-flow",
  order: 1800,
  text: ({ scope }) => (ctx.tools.get("tree_task_status", scope) === undefined ? "" : SECTION_TEXT),
});
```

段落正文（`SECTION_TEXT`，一字不改）：

```
`tree_task_*` 工具适用长线任务，当目标和资料分析完成后，如果用户要求或判断任务较为复杂，可以将任务执行计划分为目标、任务、任务执行步骤三级写入任务树，借助工具来推进项目；将目标按照可独立交付的节点分为多个任务，任务节点需要准确表述清楚需求；将任务按照“需一次性处理并交付产物”分为多个步骤；完成步骤或任务时提交后续步骤需要的 result，提交内容可以是：产物/结论/问题/有哪些需要注意的坑；执行过程上下文将会在完成时被隐藏。
```

## 2. 五个工具的描述与参数 schema

`lib/tools.js`。全部以 `tree_task_` 开头，共五个；`parameters` 是**裸 JSON Schema**
（以 `link:` 方式安装的插件从自己目录往上找不到宿主的 schemastery）。

**写树只有一个入口 `tree_task_plan`**：不填 `parentId` 就是新建一个目标，填了就是给那个
节点追加子节点。分成两个工具（原来的 `tree_task_create` + `tree_task_plan`）的时候，
两者都是"一串 `{title, detail}`"，模型会把 `create` 的顶层 `title` 混进 `plan` 的实参里。
分工具的做法已经取消，`tree_task_create` 不再存在。

五个工具共用的返回形状（`OUTPUT`）：

```js
{
  schema: {
    type: "object",
    additionalProperties: false,
    properties: { text: { type: "string" } },
  },
  render: (_args, value) => [{ type: "text", text: String(value?.text ?? "") }],
}
```

### 2.1 `tree_task_status`

```yaml
description: "查看计划树：目标、任务、子任务各自的状态与已提交的结果，以及现在该推进哪个节点。任务开头、上下文被压缩之后、或者不确定下一步做什么时，调用它。默认只展开还没结束的目标——已经做完的目标只留目标那一行，要看它的完整树就把 id 填上。"
parameters:
  type: object
  additionalProperties: false
  properties:
    id:
      type: string
      description: "可选。填目标 id 就返回那个目标的完整树（已完成的目标默认不展开）；填任务或子任务 id，就按它所在的那个目标展开。"
```

`description` 在源码里是三段字符串用 `+` 拼起来的（上面是拼接后的结果，下同）；`parameters` 里**没有 `required`**。

### 2.2 `tree_task_plan`

```yaml
description: "写计划树的**唯一**入口，两个用法：\n① 不填 parentId = 新建一个目标：这时要填 title（目标一句话）与 children（这个目标下的任务）。一个会话可以有多个目标，按调用顺序排，已经建过的目标不会被替换掉。\n② 填 parentId = 给那个节点追加子节点：父节点是目标时加的是任务，父节点是任务时加的是子任务。子任务是最低一级，不能再往下拆。\n这里的任务与子任务都是交付节点——一件能独立验收的交付内容或一个步骤，标题要能独立看懂。"
parameters:
  type: object
  additionalProperties: false
  properties:
    parentId:
      type: string
      description: "父节点 id（目标或任务），例如 t-abc123。**不填就是新建一个目标**。"
    title:
      type: string
      description: "新建目标时填：这个目标一句话说清最终要达成什么"
    detail:
      type: string
      description: "新建目标时填：目标的补充说明"
    children:
      type: array
      description: "要添加的子节点，按执行顺序。新建目标时它们是这个目标下的任务；填了 parentId 时，父节点是目标则它们是任务，父节点是任务则它们是子任务。"
      items:
        type: object
        additionalProperties: false
        properties:
          title:  { type: string, description: "子节点标题" }
          detail: { type: string, description: "补充说明" }
        required: [title]
  required: [children]
```

`description` 在源码里是六段字符串用 `+` 拼起来的，上面是拼接后的结果——其中的 `\n`
就是源码里那个换行（写成转义才能让这段代码块本身是可解析的 YAML）；`required`
**只有 `children`**——`parentId` / `title` / `detail` 都不在必填里（填了什么由
`execute` 自己判）。

### 2.3 `tree_task_done`

```yaml
description: "完成一个节点并提交它的结果（目标 / 任务 / 子任务都给它的 id）。**必须写 result**：插件会把这个节点从开始到现在的执行过程从上下文里折叠掉，换成一条只携带这段结果的汇总消息。任务的 result 写交付物与验收方式（文件在哪、怎么跑、验出什么、已知限制）；子任务的 result 一句话说清这步做了什么、结果如何就够。这次调用与它的返回都会留在上下文里，被收起的只是它前面的执行过程。"
parameters:
  type: object
  additionalProperties: false
  properties:
    id:     { type: string, description: "要完成的节点 id" }
    result:
      type: string
      description: "这个节点产出了什么。它整段执行过程会被这条结果顶替，所以要能独立看懂：任务写交付物与验收方式，子任务写清这步做了什么。"
  required: [id, result]
```

### 2.4 `tree_task_update`

```yaml
description: 修改一个节点的标题或说明。
parameters:
  type: object
  additionalProperties: false
  properties:
    id:     { type: string, description: "节点 id" }
    title:  { type: string, description: "新的标题" }
    detail: { type: string, description: "新的说明" }
  required: [id]
```

### 2.5 `tree_task_drop`

```yaml
description: "丢弃一个节点：目标、任务、子任务都能丢。丢弃目标会连同它下面的任务与子任务一起走，丢弃任务会带上它的子任务。改需求用这个，不要重建整棵树——已丢弃的节点会留在树里可查。"
parameters:
  type: object
  additionalProperties: false
  properties:
    id: { type: string, description: "要丢弃的节点 id" }
  required: [id]
```

## 3. 每种情况下的工具返回原文

工具一律返回 `{ text }`，由 `OUTPUT.render` 渲染成一个文本块。下面每一格都是**返回正文**
（换行按源码原样）。

### 3.1 树渲染（多数返回都会带一份）

`lib/plan.js` 的 `renderTree(plan, only = null)` 与 `renderGoal(goal, plan, expand = true)`
输出的是**规范的 Markdown 嵌套任务清单**，每层缩进两个空格（`INDENT = "  "`）。形状：

```markdown
- [ ] **目标** `g-xxx` <目标标题>
  - **说明**：<目标的 detail，若有>
  - **结果**：<目标结果全文>
  - [ ] **任务** `t-xxx` <任务标题> ← 当前
    - **结果**：<任务结果全文>
    - 还没有子节点，用 tree_task_plan 补上
    - [ ] **子任务** `s-xxx` <子任务标题> ← 当前
      - **结果**：<子任务结果全文>
```

| 元素 | 规则 |
|---|---|
| 节点行 | `- ` + 标记 + `**层级**` + 反引号 id + 标题；第三级写「子任务」 |
| 标记 | `[x]` 已完成（done）、`[-]` 已丢弃（dropped）、其余 `[ ]`（pending） |
| `← 当前` | 活动路径上的节点；任务行在"它就是当前任务"或"它是检查点节点"时带上 |
| `- 还没有子节点，用 tree_task_plan 补上` | 只在该任务未结束且一个子任务都没有时出现 |
| `- **说明**：` 行 | 只有**目标**有（`renderGoal` 只对 `goal.detail` 调 `pushField`）；空值不输出 |
| `- **结果**：` 行 | 只在提交过 `result` 时出现；**全文输出，一个字都不截**；多行正文逐行输出，续行比该行再多缩进两个空格，空行也带上缩进 |
| 多个目标 | 每个目标渲染成一段，段与段之间直接换行（`join("\n")`），不插空行 |
| 没有计划时 | 渲染成 `（还没有计划。用 tree_task_plan 建立目标与任务。）` |
| 指名 id 但找不到 | `找不到节点 <id>。不带 id 调用可以看到本会话的全部目标。` |

### 3.2 `tree_task_status`

| 情况 | 返回 |
|---|---|
| 不填 `id` | `renderTree(plan, null)`：全部目标，但**已经结束（done / dropped）的目标只渲染目标那一级**（`expand = isOpen(goal)`） |
| 填了 `id` | 该 id 所在目标的**完整树**（填任务或子任务 id，就展开它所在的那个目标） |
| 填了 `id` 但找不到 | `找不到节点 <id>。不带 id 调用可以看到本会话的全部目标。` |
| 没有计划 | `（还没有计划。用 tree_task_plan 建立目标与任务。）`（填不填 `id` 都一样） |

### 3.3 `tree_task_plan`

一个入口两种用法，判定顺序就是 `execute` 里的顺序：

| 情况 | 返回 |
|---|---|
| `children` 不是数组或为空 | `没有添加：children 至少要给一个子节点。` |
| 不填 `parentId`，`title` 为空 | `没有建立：不填 parentId 就是新建目标，这时必须在 title 里给出目标的标题（children 里给这个目标下的任务）。` |
| 不填 `parentId`，本会话还没有计划 | `计划已建立，目标「<目标标题>」。` + 空行 + **那个目标的树** + 空行 + `下一步：给这个目标下的第一个任务拆子任务——还是用 tree_task_plan，parentId 填那个任务的 id。` |
| 不填 `parentId`，已有计划 | `已新增目标「<目标标题>」。` + 空行 + **那个目标的树** + 空行 + 同一句"下一步" |
| 不填 `parentId`，`createPlan` / `addGoal` 抛错（兜底分支） | `建立目标失败：<错误消息>`。`children` 已在前面判过非空，所以 `createGoal` 那句"至少要有一个任务"实际到不了，这层 try/catch 是防将来改动的兜底 |
| 填了 `parentId`，本会话还没有计划 | `本会话还没有计划。用 tree_task_plan 新建一个目标：不填 parentId，填 title 与 children。` |
| 填了 `parentId`，成功（父节点是目标） | `已添加 <N> 个任务：` + 每行 ``- `<id>` <标题>`` + 空行 + **该父节点所在那个目标的树** |
| 填了 `parentId`，成功（父节点是任务） | `已添加 <N> 个子任务：` + 每行 ``- `<id>` <标题>`` + 空行 + **该父节点所在那个目标的树** |
| 填了 `parentId`，找不到父节点 | `没有添加：找不到节点 <parentId>` |
| 填了 `parentId`，父节点是子任务 | `没有添加：子任务 <parentId> 是最低一级，不能再拆` |

**写树类工具（`tree_task_plan` / `tree_task_update` / `tree_task_drop`）都只返回"本次动到的
那个目标"的树**（`renderGoal(<那个目标>, plan, true)`），不再倾倒整棵树；要总览用
`tree_task_status`。

### 3.4 `tree_task_done`

| 情况 | 返回 |
|---|---|
| 没有计划 | `还没有计划。` |
| 找不到节点 | `没有完成：找不到节点 <id>` |
| 该节点已完成 | `没有完成：节点 <id> 已经是完成状态` |
| 该节点已丢弃 | `没有完成：节点 <id> 已被丢弃，不能标记完成` |
| `result` 为空（或全空白） | `没有完成：完成<层级>必须提交结果：请在 result 里写清它产出了什么`（层级 = `目标` / `任务` / `子任务`） |
| 成功 | `tree_task消息：` + 下面五种"下一步"之一 |

成功的五种落点（按优先级判断，`lib/plan.js` 的 `continueNote`）：

| # | 情形 | 返回正文 |
|---|---|---|
| 1 | 父节点进入检查点（子节点全结束、自己还没完成） | `tree_task消息：检查点：<自称> 的<任务｜步骤>已全部结束，请确认<自称> 是否完成，如果完成请调用tree_task_done，如果还需继续，可使用 tree_task_plan 新增<任务｜步骤>继续。` |
| 2 | 整棵树都结束了 | `tree_task消息：请汇报最终结果。` |
| 3 | 同层还有下一个子任务 | `tree_task消息：接下来需要进行步骤：「<标题>」(<id>)。` |
| 4 | 当前任务没有待办的子任务（一个都还没拆，或拆下的都已结束），而整棵树还没收尾 | `tree_task消息：接下来需要进行任务：「<标题>」(<id>)。` |
| 5 | 当前目标下还没有任务 | `tree_task消息：接下来需要进行目标：「<标题>」(<id>)。` |

判断顺序就是表的顺序（`continueNote`）：检查点 → 整棵树结束 → 步骤 → 任务 → 目标，
前一条不成立才看下一条。源码里这套提示同时以 `{ lead, text }` 返回：检查点的 `lead` 是 `。`，
其余是 `，`，供"完成通告 + 下一步提示"拼成一句话；`tree_task_done` 的返回只用 `text`。

`<自称>` 的写法（`subject()`）：目标是 `目标<id>`（**不带标题**），任务是
`任务「<标题>」<id>`，子任务是 `步骤「<标题>」<id>`。

> 注意层级词在不同场合不一样：**树渲染**里第三级叫「子任务」，**注入消息与
> `tree_task_done` 返回**里第三级一律叫「步骤」。

### 3.5 `tree_task_update`

| 情况 | 返回 |
|---|---|
| 没有计划 | `还没有计划。` |
| 找不到节点 | `没有修改：找不到节点 <id>` |
| 既没给 title 也没给 detail | `没有修改：没有给出任何要改的字段（title / detail）` |
| 成功 | `已更新 <title / detail>。` + 空行 + **该节点所在那个目标的树**（改了哪个就写哪个，多个用 ` / ` 连接） |

### 3.6 `tree_task_drop`

| 情况 | 返回 |
|---|---|
| 没有计划 | `还没有计划。` |
| 找不到节点 | `没有丢弃：找不到节点 <id>` |
| 该节点已完成 | `没有丢弃：节点 <id> 已经完成，丢弃会毁掉它的结果记录` |
| 该节点已丢弃 | `没有丢弃：节点 <id> 已经被丢弃` |
| 成功 | `已丢弃：<目标「a」、任务「b」、子任务「c」>` + 空行 + **该节点所在那个目标的树** + 空行 + `<下一步提示>` |

成功时被连带丢弃的节点会按「目标 → 任务 → 子任务」的顺序列在同一行、用 `、` 分隔；
末尾的下一步提示就是 `continueNote` 的 `text`（**不带** `tree_task消息：` 前缀，
也不带前导标点）。已经结束的子节点保持原样——丢的是"还要不要做"，不改写历史。

## 4. 折叠范围的各种情况

折叠由 `agent/pre-step` 监听器完成（工具本身不注入消息、不动 surface）。规则**只看表层，
与计划树无关**。完整推导见 `docs/06-折叠范围规则.md`，这里给出可直接使用的判定表。

### 4.1 记法

写树只有 `tree_task_plan` 一个入口，所以**按实参**分两种身份：不填 `parentId` 是 `G`，
填了是 `P`。

| 记号 | 含义 |
|---|---|
| `G` | 一次 `tree_task_plan` **新建目标**（实参里没有非空 `parentId`）的调用**连同它的 `tool/result`**（下同）；**边界，且是起点首选** |
| `P` | 一次 `tree_task_plan` **追加子节点**（实参里有非空 `parentId`）的调用连同它的返回；**边界**（它之后到 `done` 之前不再折），但**不是起点首选**，可被折叠 |
| `D` | 一次 `tree_task_done` 调用连同它的返回；**边界** |
| `w` | 过程：读文件、跑命令、assistant 消息、`tool/result` 等 |
| `H` | 真人消息（`source.kind === "user"`） |

### 4.2 五条判定（按顺序）

1. **终点**：表层里**最近的一次边界调用必须是 `D`**。不是 `D`
   （说明还没走到"完成"这一步）或表层里根本没有边界调用，本轮不折。
2. **基准 floor**：上一次 `D` 的位置之后（`prevDone + 1`）。**更早没有 `D` 时，floor 是
   表层开头**（节点 0 是系统提示词，受 DSH 重写保护，永远不进替换区间）。
3. **起点**：从 floor 到本次 `D` 之间，取**最早**的那次 `G`。区间里一次 `G`
   都没有时，起点回退到 floor 自己（即上一次 `D` 的调用位置；更早没有 `D` 时回退到
   "表层第一个节点之后"）。
4. **区间**：起点那次调用的 `tool/result` **之后** → 本次 `D` 的调用**之前**。
   起点那次调用本身、以及本次 `D` 的调用与返回，都留在表层上。
   向后走时继续跳过紧邻的两样东西：起点调用自己的 `tool/result`，以及**上一次折叠落下的通告**
   （它已经是收过的结果，再收一次就会一轮轮空折下去）。
5. **两条硬约束**：区间里**夹着真人消息** → 整段不折，一个节点都不动；区间**为空**
   （`from > to`）→ 什么都不注入，不追加、不留空消息。

要点：边界调用是 `tree_task_plan` 与 `tree_task_done` 两个名字，但**起点首选只认 `G`
（新建目标）**；`P`（追加子节点）**不是起点首选**，它跟普通过程一样，落在区间里就被收走
——否则每补一次步骤，起点就往后退一次，`done` 与它之间那段过程永远收不走。
像 `D1 → w → P → w → D2`（其间没有新建目标）这种序列，起点回退到 `D1` 之后，
`w P w` 全部收走。

### 4.3 判定表

**按阶段推进读这张表**：真实会话里每次 `agent/pre-step` 只折一次，触发那一刻表层上
只到那一次 `done` 为止。所以同一个序列会分几次折，表中用"触发"列区分。

| # | 表层序列（早 → 晚） | 触发 | 起点 | 收走的区间 | 留在表层 |
|---|---|---|---|---|---|
| 1 | `G w P w D` | `D` | `G` | `w P w` | `G D` |
| 2 | `G w D` | `D` | `G` | `w` | `G D` |
| 3 | `G D`（紧邻，中间没有别的调用） | `D` | `G` | 空 → 不注入 | 全部 |
| 4 | `G P D`（只隔一次 `plan`） | `D` | `G` | `P` 的调用与返回 | `G D` |
| 5 | `G P D1 D2` | `D1` | `G` | `P` 的调用与返回 | `G D1` |
| 　 | 　 | `D2` | 回退 `D1` | 空 → 不注入 | `G D1 D2` |
| 6 | `G w D1 w D2` | `D1` | `G` | `w` | `G D1` |
| 　 | 　 | `D2` | 回退 `D1` | `w` | `G D1 D2` |
| 7 | `G w D1 w P w D2` | `D1` | `G` | `w` | `G D1` |
| 　 | 　 | `D2` | 回退 `D1` | `w P w` | `G D1 D2` |
| 8 | `D1 w G w D2` | `D2` | `G` | `w` | `D1 G D2` |
| 9 | `D1 w P w D2`（其间没有新建目标） | `D2` | 回退 `D1` | `w P w` | `D1 D2` |
| 10 | `G w H w D` | `D` | `G` | `w H w` 含真人消息 → 整段不折 | 全部 |
| 11 | 表层里找不到 `G`（被压缩遮掉） | `D` | 表层第一个节点之后 | 多半撞上真人消息 → 不折 | 全部 |

第 7 行与第 9 行是这条规则的关键：`P` **不是**起点首选，所以 `D1` 与 `P` 之间那段过程
不会漏网，`P` 自己也会被收走。完整推导、边界情形与旧版对照见 `docs/06-折叠范围规则.md`。

### 4.4 折叠通告的形态

折叠落地时追加的是一条 `user/message`（`source` 形如
`{ kind: "plugin:dsh-tree-task-flow", form: "notice", summary: <一行摘要> }`；
**不是**老写法 `{ kind: "plugin", plugin: "dsh-tree-task-flow" }`——那个在 v4 会话里
会被 DSH 的落盘校验拒掉，见 §4.6），正文（`renderSummary`）：

```
tree_task消息：隐藏了<N>条过程上下文。
读取：<路径>、<路径>
写入：<路径>、<路径>
```

- 第二、三行**只在有对应文件时**出现；路径取自工具调用的 `file_path` / `path` 参数，
  只认 `read` / `read_image`（读取）与 `write` / `edit` / `str_replace_editor`（写入），
  去重、按出现顺序；`pwsh` / `bash` 里碰过什么文件看不出来，不计入。
- 界面上的折叠标题（`summary`）：`树形任务流 · 隐藏了<N>条过程上下文`，
  涉及文件时追加 ` · 涉及 <k> 个文件`。
- **不重复提交内容**：`result` 就在这次 `tree_task_done` 的参数里，通告里不抄第二遍。
- 被折叠的节点是完成还是丢弃，通告只报条数，不区分。

### 4.5 与 `tree_task_done` 返回的关系

两者合起来才是一句完整的话：**这次 `tree_task_done` 的调用连同它的返回原样留在表层上**，
被收走的只是它**前面**那段过程：

```
[tool/result]   tree_task消息：接下来需要进行步骤：「步骤二」(s-4)。
[user/message]  tree_task消息：隐藏了4条过程上下文。
                （那一段里有文件读写时，后面另起"读取：…" / "写入：…" 行）
```

前一行是 `tree_task_done` 的**返回**，后一行是折叠**落下的通告**。注意通告报的是
"收走了多少条过程"，**不是**"哪个节点完成了"——节点的状态与结果始终在树里
（`tree_task_status` 或各工具返回附带的那份树）。

### 4.6 压缩提醒的形态

DSH 内置压缩落下检查点之后，如果这个会话有计划树，追加的也是一条同样形态的
`user/message`（`source` 同样是 `{ kind: "plugin:dsh-tree-task-flow", form: "notice" }`），
正文：

```
tree_task消息：上下文刚被压缩过，计划树没有被压缩。用 tree_task_status 取回当前进度、各节点已提交的 result，以及下一步该推进哪个节点。
```

- 界面上的 `summary`：`树形任务流 · 上下文被压缩，计划树仍在`。
- 与折叠通告的区别：它用 `surfaceOp: "append"`（只追加、不替换），
  折叠通告用的是 `replace`。
- 认压缩的依据是表层上那条 `user/message` 的 `source`——**两种形状都认**：
  v4 原生的 `{ kind: "compact-checkpoint", compactionId, … }`，与还没迁移的
  v3 会话里的老写法 `{ kind: "plugin", plugin: "compact" }`。**不是**
  `compaction/summary` 事件——那个事件不带 `surfaceOp`，根本不在表层里。
- 同一个检查点只提醒一次，位置记在 `surfaces/<sessionId>.json` 的 `compactionNoticeAt`。
- 实现与已知限制见 `lib/compaction.js` 与 `docs/02-DSH插件开发方案.md` §4.8。

## 5. 状态文件

全部在 `$DSH_HOME/dsh-task-tree/` 下，**以 `sessionId` 为键**（`lib/store.js`）：

| 文件 | 内容 |
|---|---|
| `plans/<sessionId>.json` | 计划树（每个会话一棵；`tree_task_plan` 不填 `parentId` 时追加目标，不替换整棵树） |
| `surfaces/<sessionId>.json` | 三层进度游标 `{ key, cursor }` 与压缩提醒的已提示位置 `compactionNoticeAt`——**不参与折叠**，只给界面看 |
| `held/<sessionId>.json` | `{ sessionId, paused, stopped, at }`：「被按住」的持久状态，重启后仍然有效 |

- 写入一律走「临时文件 + rename」；读到的坏文件按空状态处理。
- 插件**绝不直接写会话日志**：会话里的一切都走 `session.append()`。
- `held` 的两半互补更新（`paused` 归暂停闸门、`stopped` 归自动续行），两份都不是 `true` 时删文件。
