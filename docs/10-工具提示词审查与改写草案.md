# 工具提示词审查与改写草案

审查对象：插件**面向模型的那一层**——`lib/prompt.js` 的系统提示词段落，加上 `lib/tools.js` 里十个工具的 `description` 与参数 `description`。
不涉及工具返回文本、折叠实现、面板。

依据：`lib/tools.js`、`lib/prompt.js`、`lib/render.js`、`lib/notes.js`、`lib/requirement.js` 的实际实现，以及 `docs/09-需求与任务模型.md`、`docs/06-折叠范围规则.md`。

---

## 0. 结论

现状：模型每次请求都要付 **3136 字**的提示词税，其中工具 `description` 1779 字、参数 `description` 738 字、系统段落 420 字。

三个主要问题：

1. **规则重复**。`prompt.js` 开头的注释自己立了规矩：「同一句话写在两处，只会让它在每一次请求里占两份位置，而模型真要调用时读的始终是 `description`」。但正文至少五处违反了这条规矩（拆分口径、立刻完成、result 写法、拉列表、草稿确认）。
2. **内部机制泄漏**。折叠、边界、游标、面板行为、版本号这些模型改变不了的东西写进了工具描述，「折叠」一词出现在五个工具描述和段落里。
3. **描述与实现不一致**，其中三处会让模型做错事：`create` 自称「开工」、`prerequisites` 的 `id` 与 `ids` 关系反了、`confirm` 写着「必给 title」而实现允许沿用草稿标题。

建议按「段落讲循环、描述讲那一步、一条规则一处」重写，目标总量 **1800 字左右**（降四成），同时把三处与实现矛盾的表述改对。

## 2. 问题清单

### 2.1 会误导模型（优先修）

**（1）`create` 自称「开工那一下」，与 `start` 打架。**
`lib/tools.js:244-245`：「**它是「开工」那一下**——折叠上下文时，插件认这次调用作为「这一轮从哪儿开始」」。
而 `tree_task_start` 的描述才叫「开始一条需求」。同一个会话里两个工具都叫「开工」，模型很可能在确认后只 `create` 不开工，或反过来重建一条草稿。折叠边界是内部机制，模型知道它并不能让它做得更对。

**（2）`prerequisites` 的 `id` 与 `ids` 说反了。**
`lib/tools.js:310`：「prerequisites：设置前置需求（ids）」。
实现（`lib/requirement.js` 的 `setPrerequisites`）：`id` 是**被设置的那条需求**，`ids` 是**它的前置列表**，而且是**整体替换**、可以给空数组清空。照现在的描述，模型会把 `id` 当成前置实体、把 `ids` 当成被设置者。

**（3）`confirm` 要不要 `title`，描述与实现不一致。**
`lib/tools.js:305`：「confirm：把草稿转成正式需求（必给 title……）」。
实现（`confirmRequirement`）：草稿里已有标题时沿用，`title` 可不传。描述强迫模型多传一次标题，或让模型以为复用标题会出错。

**（4）`status` 说「含已归档与草稿的计数」，实际返回的是完整列表。**
`lib/tools.js:177`。`renderList` 会把已归档需求逐条列出、草稿逐条列出。模型按描述会以为只能看到数量，于是用 `ids` 一条条查已归档需求。

**（5）`status` 没说 `include` 只在给 `ids` 时生效，也没说 `ids` 优先于 `match`。**
代码里 `include` 只在 `ids.length > 0` 的分支被使用；`match` 与 `ids` 同给时，`match` 被静默忽略。

**（6）`note` 的查询条件说错了。**
`lib/tools.js:774`：「不给 key 就是查」。
实现是 `key` 与 `text` **都为空**才查；只给 `key` 不给 `text` 会走写入路径并被拒（「笔记正文不能为空」）。模型按描述“只给 key 查一下”会拿到失败返回。

**（7）`requirement` 的 `id` 在 schema 里不是必填。**
`required: ["action"]`（`lib/tools.js:336`），但除 `question` 外六个动作都要 `id`。模型漏填时返回的是「找不到需求 」（空编号），信息量极低。

### 2.2 重复与冗余

- 拆分口径、立刻完成、result 写法在段落与工具描述间**逐字重复**（见上表）。
- `done` 的 result 写法重复第三遍：`description` 说「任务写交付物与验收方式」，`result` 参数描述又说「任务写交付物与验收方式，子任务写清这步做了什么」。
- `drop` 与 `delete` 互相解释：两份描述各花一句讲对方。
- `create` 描述里的「三种来源」：面板建条目、用户一口气写全，都不是模型通过 `create` 触发的动作，讲了也用不上。

### 2.3 机制泄漏

「折叠」出现在 `create`、`start`、`done`、`plan`、`note` 五个描述和系统段落里。模型既不知道这个词的定义，也改不了这个行为，只需要知道后果的一句话：「完成后这段过程会从上下文里收走」。

同类还有：
- `create`：「草稿不占上下文」——不准确，草稿会作为一行出现在列表里。
- `requirement`：「不叫醒用户」——面板行为。
- `plan`：「把它们列成节点只是白占一个格子，**还会把折叠卡住**」——后者是无法验证的机制解释，而且容易让模型误解成“只要不 plan 就不会被折”。
- 段落：「折叠发生在完成的那一刻，攒着的那段过程会一直留在上下文里陪跑」——这句对行为的约束力在“别攒”，不在“折叠”。

### 2.4 结构与风格

- 420 字的段落**没有分段**，关键动作「开工先拉列表」在第二句，完成规则在最后一段。模型读到的顺序与工作顺序不一致。
- 段落**一律不点名工具**（`verify-entry.mjs:191-194` 钉着），于是只有「用工具」「它」这种指代。模型要在“该调哪个”上自己做映射，省下的十来个字换不到清晰。
- 否定句密集：`create` 一句、`plan` 一句、`update` 一句、`delete` 一句、段落一句。一段里四五个否定会互相掩盖。
- 加粗过多：`requirement` 一段四处 `**`，`done`、`create` 各三处。强调多了等于没强调。
- `tree_task_update` 整段是一句“别用我”，占了十分之一的工具位。

### 2.5 参数 schema

- `plan.children` 没有 `minItems: 1`，缺了才在运行时报错。
- `drop` / `delete` 的 `id` 与 `ids` 二选一，schema 表达不了，描述里也没说清。
- `done.id` 的描述写「需求编号 / 任务 id / 步骤 id」，返回文本里的层级词是「步骤」；同层级的树渲染里叫「子任务」（`render.js` 用「步骤」，`plan.js` 的旧树渲染用「子任务」）。模型可见文本要统一成「步骤」。

## 3. 优化原则

1. **模型可见文本只回答三个问题**：什么时候用我、参数怎么填、用了必须守什么。凡是模型改不了的（折叠、边界、游标、面板、存储）一律删。
2. **一条规则只写一处**。时机与顺序归系统段落，动作约束归对应工具的 `description`，字段边界归参数 `description`。
3. **系统段落点名关键工具**。`tree_task_status`、`tree_task_create`、`tree_task_requirement` 三个名字直接写出，其余仍交给各自的描述。代价是十来个字，换来指代明确。
4. **否定句只保留必要的一条**，而且必须说明“该用哪个”而不是只说“别用”。
5. **术语统一**：需求 / 任务 / 步骤 / 草稿 / 暂定版本 / 结果。模型可见文本里不出现「目标」「子任务」「检查点」。
6. **字数上限**：系统段落 ≤ 260 字，单个工具 `description` ≤ 280 字，单个参数描述 ≤ 60 字。

## 4. 改写草案

### 4.1 系统提示词段落

```js
export const SECTION_TEXT =
  "`tree_task_*` 工具管这个会话里用户要什么：需求记用户提的要求，任务与步骤记你打算怎么把它做出来，" +
  "笔记记跟这次工作有关、但不属于任何一条需求的事实与偏好。\n\n" +
  "开工先调 tree_task_status 拉一次需求列表——它不常驻上下文，不拉就不知道这个会话里还有什么事。" +
  "用户提出的事先用 tree_task_create 记成草稿，跟用户谈清标题与简介、转正之后再开工；" +
  "用户改过的需求会以暂定版本等你确认，看到待确认变动先处理它再往下做。\n\n" +
  "每完成一个任务就立刻调一次完成工具，别攒到最后补——攒着的那段过程会一直留在上下文里陪跑。";
```

约 230 字，三段对应「这组工具是什么 / 一次工作的顺序 / 唯一必须记住的时机」。拆掉：拆分口径（归 `plan`）、result 写法（归 `done`）、草稿确认细节（归 `create` / `start`）、笔记覆盖（归 `note`）。

### 4.2 十个工具的 `description`

**`tree_task_status`**

> 取回这个会话的需求。不填参数返回需求列表（活跃、已归档、草稿），并展开当前进行中的那条需求的任务与步骤；填 ids 按编号取回详情。开工第一步、上下文被压缩之后、或不确定接下来做什么，先调它——需求列表不常驻上下文。

参数：
- `ids`：需求编号，例如 `["R1","R5"]`。填了就不返回列表。
- `match`：按关键词过滤需求，匹配标题、简介、详情；与 `ids` 同给时只按 `ids` 返回。
- `include`：只在给 `ids` 时生效。要哪几节：`detail`（简介、前置、详情）、`versions`（版本历史）、`tasks`（任务与结果），默认 `detail` 和 `tasks`。

**`tree_task_create`**

> 把用户刚提出的一件事记成需求草稿。草稿要跟用户谈清标题与简介、用 tree_task_requirement action=confirm 转正，才算正式需求。用户在面板上建的那条、或者一口气说全的，也一样先落草稿再确认。一条需求可以对应毫无关联的目录或项目，不要按项目归类。

参数：
- `title`：标题，不超过 50 字。
- `intro`：简介，不超过 200 字，说明用户要什么。
- `detail`：详情，不限长。用户原话、背景、约束都可以放；只有 AI 能写。
- `tasks`：用户一口气说清了要做哪几件事时顺手带上；没说清就留空，开工时再拆。

**`tree_task_requirement`**

> 改需求：确认草稿、改正文、确认用户提交的暂定版本、退回提问、归档、设前置。除 question 外都要给 id。
> - confirm：草稿转正。草稿已有标题可以不传 title，要改就一起传。
> - update：直接改正文，当场生效、版本 +1。有暂定版本待确认时先 confirmChange 或 question；草稿不能 update。
> - confirmChange：确认用户提交的暂定版本。看到待确认变动先做这个，再干别的。
> - question：暂定版本有歧义，不转正，把要问的话写进 question。
> - archive / unarchive：只影响是否出现在活跃列表，与完成状态无关；给 ids 可批量。
> - prerequisites：给 id 这条需求设前置，ids 是前置需求编号，会整体替换原前置，给空数组就是清空。前置不是闸门，没做完也能开工。

参数：
- `id`：需求编号，例如 R3。archive / unarchive 可改用 ids 批量。
- `action`：要做的动作。
- `title`：标题，不超过 50 字。
- `intro`：简介，不超过 200 字。
- `detail`：详情，不限长。
- `change`：这次改了什么，写进版本历史。confirm 时默认「初始需求」。
- `question`：action=question 时要问用户的话。
- `ids`：prerequisites 时是前置需求编号；archive / unarchive 时是要批量处理的需求。

**`tree_task_plan`**

> 给需求追加任务，或给任务追加步骤。任务是能独立验收的交付；步骤是一次性能做完的那一下，不能再拆。读资料、看文档、看需求详情不算任务——那是开工前就该掌握的信息，列成节点只会白占位置。建新需求用 tree_task_create。

参数：
- `parentId`：父节点 id：需求编号或任务 id。
- `children`：要追加的子节点，按执行顺序；父节点是需求时是任务，是任务时是步骤。至少给一个。

**`tree_task_start`**

> 开工一条正式需求：取回它的详情（简介、详情、任务与结果），并把上一次折叠之后的过程从上下文收走。开工前先把要读的文件、文档、已有结论读完再拆任务，没摸清就拆多半要返工。草稿不能开工，先 confirm。

参数：`id`：要开始的需求编号。

**`tree_task_done`**

> 完成步骤、任务或需求，记下 result。完成后这段执行过程会从上下文里收走，只留这条结果，所以 result 要能独立看懂。id 给哪一级都行。result 怎么写：步骤一句话说清做了什么；任务写交付物与验收方式（文件在哪、怎么跑、验出什么、已知限制）；需求写总结（做了什么、结论、坑、给后续的注意），别的需求靠它快速查阅。完成需求不用问用户，你判断做完了就完成它。

参数：
- `id`：要完成的节点：需求编号、任务 id 或步骤 id。
- `result`：这个节点产出了什么。整段执行过程会被它顶替，所以要能独立看懂。

**`tree_task_update`**

> 改任务或步骤的标题、说明。改需求正文用 tree_task_requirement action=update，因为要留版本历史。

参数：`id`、`title`、`detail`。

**`tree_task_drop`**

> 放弃节点：这件事不做了，划掉留在树里可查。放弃需求会连同它下面没做完的任务与步骤一起放弃，已完成的不动。支持批量，给 ids。

参数：`id`：要放弃的节点 id；`ids`：要放弃的一批节点 id。

**`tree_task_delete`**

> 删掉节点，物理摘除、不可逆、不看状态，连同下面的子节点一起。只在内容本身写错、建重、结果记错地方时用；「这件事不做了」用 tree_task_drop，那个留痕。支持批量，给 ids。

参数：`id`：要删除的节点 id；`ids`：要删除的一批节点 id。

**`tree_task_note`**

> 笔记：跟这次工作有关、但不属于任何一条需求的事实与偏好（构建入口、踩过的坑、对产出的要求）。给 key 和 text 就是写；同一个 key 再写是覆盖、修订号 +1，所以 key 起短一点、稳定一点。要查就只给 query，什么都不给就是全部。上下文里同名的笔记可能有多份（早先的过程里写过旧值），以修订号大的为准。

参数：`key`、`text`、`query`。

### 4.3 改后体量估算

段落约 230 字，十个描述合计约 1250 字，参数描述约 450 字，总量约 1900 字，比现在少四成。`requirement` 仍是最大的一个（约 300 字），因为七个动作共用它。

## 5. 落地步骤

1. 改 `lib/prompt.js` 的 `SECTION_TEXT`，同步更新头注释（那句“同一句话写两处”要和新正文一致）。
2. 改 `lib/tools.js` 十个 `description` 与参数描述。`OUTPUT`、`execute`、边界工具名都不动。
3. 改 `verify-entry.mjs` 的提示词断言（见第 6 节）。
4. 同步 `README.md`「十个工具」小节和「折叠按什么切」里被改动的措辞。
5. 跑全套自检：`verify-entry.mjs`、`verify-tools.mjs`、`verify-source.mjs`、`verify-compaction.mjs`。

## 6. 自检调整

- 删掉「文本不逐个点名工具」（`verify-entry.mjs:191-194`），改成「段落最多点名三个工具」：`(SECTION_TEXT.match(/tree_task_[a-z]+/gu) ?? []).length <= 4`（含通配 `tree_task_*`）。
- 新增字数上限：段落 ≤ 260 字；每个工具的 `description` ≤ 280 字。当前 `requirement` 的 365 字会先被这条挡下来。
- 新增机制词黑名单：模型可见文本不出现「折叠的边界」「游标」「不叫醒」「白占一个格子」。`折叠` 本身只在 `start` 描述里保留一次（「上一次折叠之后的过程」），可放行。
- 新增重复检查：段落不得包含 `一件能独立验收`、`交付物`（这两条归 `plan` 与 `done`）。

## 7. 这次不改的

- **工具名与工具划分不改**。`create` / `start` / `done` 是按工具名认的折叠边界（`docs/06`），改名要同步 `region.js` 的 `BOUNDARY_TOOLS`、面板、文档、旧会话；收益只是名字更顺，不值。`drop` 与 `delete` 也不合并：两个名字的可发现性比少一个工具更重要。
- **`tree_task_update` 不去掉**。它挡的是“模型拿它改需求正文”，压短即可。
- **工具返回文本不动**。不在本次范围。

## 9. 第二轮：按用户设计重写（0.3.14 工作区，未发版）

用户明确的设计流水线：

1. `tree_task_create` 记录需求草稿；
2. `tree_task_requirement` 的 `update` 逐次修改正文，每次只改给出的字段，修改后仍是草稿；可以多轮对话、多次更新；
3. `confirm` 确认并生成版本（第一次 v1，之后每次确认 +1）；
4. 读取完成工作所需的文件与文档；
5. `tree_task_start` 记录开工点，并把上一次折叠成功位置到本次调用之前的过程折叠掉；
6. `tree_task_plan` 创建任务与步骤；
7. 每完成一个步骤、任务或需求，立刻调用一次 `tree_task_done`，不合并；任务级 `done` 折叠到上一个 `done` 或 `start`，需求完成时折叠整条。

这一轮同时改了实现，因为原实现的草稿不能 `update`、`update` 会直接升版，与第 2、3 步冲突：

- `updateByAi`：草稿与已确认需求都能改；只改给出的字段；改完状态回到草稿；不生成版本（版本只在 `confirm` 时落）。
- `updateByUser`：草稿直接写进正文，不产生暂定版本；已确认需求仍走暂定版本。
- `tools.js`：十个工具的描述与参数说明按上述流水线重写；`start` 的返回文本去掉口语；`done` 明确「每完成一个步骤调用一次」；折叠锚点写成「上一个 done 或 start」。
- `prompt.js`：段落重写为「结构 → 流水线 → 完成时机」三段，段内点名 status / create / requirement / start / done。
- 自检同步：`verify-requirement.mjs`（草稿可改、update 回草稿不升版）、`verify-tools.mjs`（描述断言、update 流程、create 返回、start 返回）、`verify-entry.mjs`（段落断言、字数上限 340、点名上限 6）。
- 文档同步：`docs/09` §3.2/§3.3/§3.4、`docs/06` §1、`README.md` 十工具表与折叠规则。
